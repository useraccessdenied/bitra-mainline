## Incident: Phosh "stuck" after the clean flash (2026-11-27), fixed
- Symptom: black panel, `tinydm` failed ("respawned too many times"): the autologin session started and ended within a second, over and over (each pass leaked a D-Bus daemon).
- Cause: `/usr/bin/gnome-session` (a wrapper script) re-executes itself through `bash -c "exec -l $SHELL -c 'exec gnome-session -l ...'"`. The builder wrote a one-line `/bin/bash` stand-in (`exec /bin/busybox ash`, for the bitra-agent's shell wrapper) AFTER installing packages, replacing the real `bash`; the stand-in ignores `-c`, so `gnome-session` exited 0 without starting anything. The previous live system never showed it because its real bash had been installed by hand earlier.
- Found by tracing the session (`sh -x /usr/bin/tinydm-run-session`, `~/.phoshdebug` to wrap `gnome-session`, `sh -x /usr/bin/gnome-session`). A getty on tty1 and the kernel command line were ruled out.
- Fix on the phone: the real bash 5.3.9 (taken from the Alpine package on the host) copied over `/bin/bash` (the stand-in is saved as `/root/bash-shim.bak`); Phosh then ran (`phoc`, `gnome-session-binary`, `phosh`, `squeekboard`). Fix in the builder: `bash` is an explicit package, the stand-in is only created when no real bash exists, and the build asserts that `/bin/bash` is an ELF. Rebuilt `releases/alpine-rootfs-release.ext4` sha256 `f7ec53a091a03d3f59f5ba7856340c1111c57065c6f2cbca87910079ccada5a8` (the flashed one was `713f1545...`); the phone now equals it except for being repaired live, no reflash needed.
- Lesson: boot the production image to the Phosh home screen before calling it done (the check list should include `pidof phosh`).

## Distribution design (owner's decisions, 2026-11-27)
- **Release = two `.img` files**: `boot.img` (kernel + DTB + release initramfs) and `userdata.img` (the rootfs). The same `boot.img` serves every OS; Alpine, Mobian and Fedora Plasma Mobile differ only in `userdata.img` (docs/37). `userdata.img` is flashed with fastboot, has `bitra.root=userdata` as its only hook, and is **not** made partition-sized: it is a small ext4 image in Android sparse format (`img2simg`; fastboot flashes sparse images in chunks) that grows to the partition on first boot (`bitra-growfs` today, `systemd-growfs` or resize2fs on the systemd distros). An exact-fit full-size image would break on a different storage size and is impractical to flash. Fastboot flashing of `userdata` on this bootloader is still to be tested (we have used a RAM-booted flasher so far).
- **Release vs test builds.** Release: no USB-NCM gadget, no telnet, no DHCP server, no shell in the initramfs, no diagnostics on the panel; if the root partition does not appear within 120 s the initramfs reboots. Test: today's behaviour (NCM + telnet at 192.168.2.15 for `bitra-agent`). The USB-link lapse problem (docs/known-issues) is therefore a test-image issue only. Recovery on a release phone is the bootloader (fastboot, key combination); with an unlocked bootloader anyone can flash anything, so the initramfs hardening only removes accidental exposure.
- **Boot logo.** The release initramfs draws a logo on the panel (`tools/make-boot-logo.py`: raw XRGB8888 frame, gzip, written to `/dev/fb0` as soon as the msm driver creates it, 1080x2400, stride 4352 measured on the phone; `BOOT_LOGO_PNG=file.png` swaps the picture). Before the msm driver probes (~10-25 s) the panel shows whatever the bootloader left; the OS draws its own splash after the handoff. The kernel prints nothing on the panel (`tty0` is not a console, `loglevel=0`). Text the owner still sees before OpenRC is to be identified (kernel `[ 0.000]`, initramfs `bitra-debug:`, OpenRC `* Starting`, or the Oplus bootloader's unlocked-state screen, which no image can remove).
- **Access.** No Tailscale in release images (the user installs and manages it; the kernel has `TUN` and nftables as modules). Test images keep USB-NCM; the user's login/lock password is the user's responsibility (`bitra` or `123` is accepted for now), sshd stays key-only.
- **Updates and integrity.** The OS's own package manager updates the userland. Kernel (`boot.img`) and firmware updates are published on the owner's site as images with SHA-256 hashes only (no signing, no update service). Packages must hold back any distro kernel so a distro upgrade cannot replace the kernel.
- **Vendor firmware: correction.** `super` is not unused. The stock `vendor` and `odm` images inside it are where the builders take the sensor configuration tree (`vendor/etc/sensors/config`, `odm/etc/sensor/config`, `sns_reg_config`) and the Adreno 650 ZAP shader (`vendor/firmware/a650_zap.*`). The DSP firmware (adsp/cdsp/slpi) comes from the `modem` partition, and the sensor registry from the owner's `persist` backup. A release must not ship the vendor files; the plan is to extract them on the phone from the user's own partitions at first boot into the rootfs (so `super` can be reused afterwards), with the manifest hashes as the check. Not done yet, and the ZAP shader needs a decision: the GPU asks for it before the root is mounted, so it is currently inside `boot.img` (a redistribution problem if `boot.img` is published; options: published `boot.img` without it and a first-boot step that adds it and restarts the GPU, or each user builds their own `boot.img`).
- **`super` as user storage**: allowed after first boot has copied the vendor files; formatting it before that removes the only on-phone source (the realme firmware zip remains a source). The partition is not written by any of our images.

## Decisions 2 (2026-11-27): ROM-style release, postmarketOS-style firmware
- **Release = three flashable images**: `boot.img`, `userdata.img` (Android sparse, small, grows on first boot), `super.img` (the vendor image). The user can be on any realme firmware: the DSP firmware is shipped in `super.img` instead of being read from the user's `modem` partition. Hashes (SHA-256) are published next to them; no signing, no update service; the vendor files are published and marked **proprietary** on the owner's site (as postmarketOS does with its device firmware packages). Redistributing the GPU ZAP shader and the DSP/sensor files is the owner's decision.
- **`super.img` contents** (plain read-only ext4, label `bitra-vendor`, written to the start of the `super` partition; no Android dynamic-partition metadata; ~50 MiB): `firmware/qcom/sm8250/realme/bitra/` (adsp, cdsp, slpi sets from `modem.img` + `a650_zap.*`), `sensors/config/*.json` (**all** 91 + odm configs, no prune list; sensors take ~100 s to come up, accepted), `sensors/sns_reg_config` (default registry template), `VERSION`, `MANIFEST.sha256`, `PROPRIETARY.txt`. Built from the owner's firmware zips by `tools/build-super-img.py --rom-zip <full package> [--firmware-zip <firmware zip>]` (`simg2img` + `fsck.erofs --extract` for vendor/odm, `bitra-firmware.py` for the DSP sets, `mke2fs -d`).
- **Not in any image**: the per-unit sensor registry (calibration) and the Wi-Fi OEM board data (`bdwlan.elf`) come from the phone's own `persist`, mounted read-only (owner: read-only plus copy). `bitra-persist` (first boot) copies `sensors/registry` into the served directory; the Wi-Fi board-data step is still to do (release images use the generic linux-firmware `board-2.bin`; the OEM entry needs a card reload, since ath11k probes before the root is mounted).
- **Wiring**: the release initramfs mounts `super` read-only at `/vendor`, binds its firmware directory over `/lib/firmware/qcom/sm8250/realme/bitra` (so the GPU finds the ZAP and the DSPs their firmware), and moves `/vendor` into the new root; the rootfs service `bitra-vendor` binds firmware, `sensors/config` and `sns_reg.conf` to where the kernel and hexagonrpcd look. If `super.img` was not flashed the service says so and the phone boots without GPU/DSP/sensors.
- **Pipeline**: `tools/release.py VERSION --rom-zip ... --firmware-zip ...` builds `releases/VERSION/{boot.img,userdata.img,super.img,SHA256SUMS}`; users run `fastboot flash boot|userdata|super`. Same recipe for the later Mobian and Fedora Plasma Mobile `userdata.img` files; `boot.img` and `super.img` are shared. `AGENTS.md` now lists `super` as an allowed write target.
- Open: flash test of sparse `userdata.img` and plain `super.img` with fastboot on this bootloader; the Wi-Fi OEM board data; whether the DSP/GPU firmware requests see the bind mount early enough (checked on the first release boot); empty-registry behaviour (the default template may be enough now that SMEM 130 is filled).

## Flashing order (owner, 2026-11-27): userdata LAST, erase it first
Fastboot on this bootloader hangs after a `userdata` flash: `getvar` times out and only `fastboot reboot` works (the owner then had to reboot to the bootloader by hand). So the order for the release is:
1. `fastboot flash super super.img`
2. `fastboot flash boot boot.img`
3. `fastboot erase userdata`
4. `fastboot flash userdata userdata.img`
5. `fastboot reboot`
`userdata` is always the last write, and it is erased before it is flashed. Reason for the erase (my diagnosis of the 0.1-test no-Phosh boot, to be confirmed): `img2simg` turns all-zero blocks into DONT_CARE chunks, and `mke2fs -E lazy_itable_init=1` leaves the inode tables zero, so a sparse flash over an un-erased partition keeps the OLD partition's blocks there and the new ext4 reads garbage inodes. (The 0.1-test flash did `super`, `userdata`, then `boot`, and had to be recovered by hand.) The agent's `flash` command needs an `erase` step and a flash-order check for this.
