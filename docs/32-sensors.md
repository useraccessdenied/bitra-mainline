## What it takes (all found the hard way; every item was necessary or confirmed harmless)
1. **SLPI remoteproc** (`&slpi { firmware-name = "qcom/sm8250/realme/bitra/slpi.mdt"; status = "okay"; }`, region `slpi_mem` 0x90600000 / 21 MiB; firmware = `slpi.mdt` + `slpi.b00..b21` from the stock modem partition, `tools/extract-dsp-firmware.py`).
2. **`hexagonrpcd-sdsp`** (Alpine `hexagonrpcd` + `-openrc` + `-udev`; the udev rule makes `/dev/fastrpc-sdsp` owned by `fastrpc`) started **after** the SLPI is up. The DSP asks for files exactly once at its boot; a daemon that is not attached then leaves SSC without a registry (`'registry' sensor unavailable`) until the SLPI is restarted (`echo stop/start > /sys/class/remoteproc/remoteproc0/state`).
3. **Served directory** `/usr/share/qcom/sm8250/realme/bitra/` (`hexagonrpcd_fw_dir` in `/etc/conf.d/hexagonrpcd-sdsp`; layout found with `inotifyd`):
   - `sensors/config/*.json`: stock vendor `/vendor/etc/sensors/config` + odm `/odm/etc/sensor/config` (91 files). The DSP opens `/odm/etc/sensor/config` **literally**: symlink it to the served directory.
   - `sensors/sns_reg.conf` = stock `sns_reg_config`.
   - `socinfo/{hw_platform,platform_subtype,platform_subtype_id,platform_version,soc_id,revision}`: the SSC config selection reads the platform identity from `/sys/devices/soc0`, which mainline's socinfo only partly provides. Values used: `hw_platform=MTP`. Evidence: the stock registry holds `alsps_platform.prox*` written during the stock run (real proximity calibration: offset 296, 3 cm threshold 797), so the generic `alsps` driver (`kona_qrd_alsps.json`: I²C bus 5, address 0x46, IRQ 122, **MTP only**) is the one that ran on this phone. QRD was tried too (it selects the TMD2725 config, needs `platform_version=65536`; accelerometer came up faster, ~73 s vs ~110 s) but made no difference for proximity/light, `soc_id=356`, `revision=2.1`, `platform_subtype=Unknown`, `platform_subtype_id=0`, `platform_version=65536`.
   - `sensors/registry/registry/` + `sensors/registry/sns_reg_version`: **the stock registry (563 entries + version) is required.** With an empty registry the DSP writes nothing and no sensor ever appears (tested, 5 min). It is device specific (this unit's calibration): `tools/extract-sensor-registry.py` extracts it from the owner's `persist` backup into the gitignored `third_party/sensors/registry`; the builder includes it when present and warns otherwise. Must be writable by `fastrpc`.
4. **Timing**: SSC takes about **100 s** after the daemon starts before the sensors answer (`'registry' sensor unavailable, retrying` until then).
5. **iio-sensor-proxy** (3.9): the stock udev rule maps the SDSP only to `ssc-light ssc-compass`. `rootfs-overlay/etc/udev/rules.d/81-bitra-iio-sensor-proxy.rules` adds `ssc-accel ssc-proximity`; the proxy then reports `Has accelerometer`. It exits if no sensor is found at all, and a stale daemon claim on the compass made `monitor-sensor` disconnect before the rule existed.

The image builder (`scripts/build_alpine_rootfs.py`) installs the packages, SLPI firmware, config tree, socinfo files, registry (if extracted), the `/odm` symlink, conf.d, udev rule and the service.

## Not working yet
- **Magnetometer / compass / rotation vector**: `No 'mag'` / `No 'rotv'`. Stock lists an MMC5603NJ (`kona_qrd_mmc5603nj`, MTP) and an AK0991x config; check the platform selector and the registry entries (`mmc5603x_0_platform.*`).
- **Proximity, ambient light, magnetometer, SAR (everything on I²C): not enumerated** (`No 'proximity'` / `No 'ambient_light'` / `No 'mag'`), with MTP and with QRD. Findings of the deeper check (2026-11-22):
  - Bus pattern from all stock configs: the working IMU (BMI26x/ICM4x6) is on **SPI** (`bus_type=1`, instance 3, IRQ 123); every sensor that does not appear is on **I²C** (`bus_type=0`): alsps/TMD2725/SX933x/LPS22HH on instance 5 (alsps addr 0x46, IRQ 122), MMC5603NJ magnetometer on instance 1 (addr 0x30), rear ALS on instance 4. All use the same `/pmic/client/sensor_vdd[io]` rails as the IMU, so power is not the difference.
  - The AP does not claim any of TLMM pins 100-129 except 110 and 118 (touch/haptic): no pin conflict with the interrupt pins 112-123.
  - The daemon logs thousands of failed DSP writes of `/mnt/vendor/persist/sensors/registry/registry/../temp.json` and `sns_reg_version` (the DSP opens these **literal** paths; only `/sensors/...` and a few others are mapped under `-R`), the missing `oemconfig.so`, `wigig_sensing.so`, `sns_bring_to_ear.so` and `/mnt/vendor/persist/engineermode/cali_coe` (Oplus ALS calibration). Pointing `/mnt/vendor/persist/sensors` at the served directory (and an empty `engineermode`) did **not** change the result: no registry file is rewritten and no I²C sensor appears. None of those files exist in the stock ROM either (no `oemconfig.so`).
  - The downstream kona DT has no description of the SSC I²C engines (the SLPI firmware owns them), so there is nothing to compare there. The kernel log shows nothing from the SLPI.
  - Remaining ideas: SSC/SLPI diagnostic logging (F3/diag over QMI or from the SLPI memory), checking whether the I²C engines need an AP-side vote (GDSC/clock/interconnect for the SSC QUP) that the downstream `msm-ssc-sensors`/`pil` code provides, comparing with another mainline SM8250 phone that has working SSC I²C sensors (if any), and the TZ/xPU assignment of those QUP engines.
- **Mount matrix** (done, owner-verified: Phosh rotates correctly in portrait and both landscapes): raw SSC readings from a buzz-cued pose test were flat/screen-up `(0.36, 0.01, -9.81)`, portrait/top-up `(-0.53, -9.82, -0.79)`, landscape/top-left `(9.82, -0.01, -0.98)` m/s². Z must be flipped so that a phone lying flat reads `face-up`. My first guess `diag(1,-1,-1)` (from the usual "reading = +g along the up axis" convention) made the UI 180 degrees off in portrait and landscape, because iio-sensor-proxy treats upright portrait as Y < 0. The working value is **`ACCEL_MOUNT_MATRIX="-1, 0, 0; 0, 1, 0; 0, 0, -1"`** (udev property on the `fastrpc-sdsp` device, in `81-bitra-iio-sensor-proxy.rules`). Phosh only attaches to the proxy at session start, so after (re)starting the proxy the session must be restarted (`rc-service tinydm restart`); the quick-settings rotation toggle appears once Phosh sees the accelerometer.
- **Boot ordering** (done): the new OpenRC service `bitra-sensors` (needs `hexagonrpcd-sdsp`, `dbus`) waits in the background until `ssccli` returns an accelerometer sample, restarts `iio-sensor-proxy` (it exits when it finds no sensor; the SSC needs ~100 s) and, because Phosh only connects to the proxy at session start, restarts the Phosh session once if it did not claim the accelerometer. Pitfall: `rc-service tinydm restart` only stops the autologin supervisor, the old compositor keeps running orphaned and a second full session is stacked on top; the service stops tinydm, `killall`s phoc/phosh/gnome-session-binary and starts tinydm again. On a real cold boot with `mainline-boot-7` the proxy had the accelerometer at uptime ~123 s.

## Update 2026-11-27: the I²C sensors need the SMEM sensor inventory (item 130) - FIXED
The SLPI firmware (Oplus build) does not probe its I²C sensors; it reads the inventory (chip id, bus number, direction, IRQ per sensor type) from **SMEM item 130**, which the downstream kernel's `oplus_sensor_devinfo` driver fills from the DT node `oplus,sensor-devinfo` before the SLPI boots. Mainline never filled it, so only the default SPI IMU appeared (all the earlier "persist/registry/platform/pins" experiments above were looking in the wrong place). Found through a web search (omnipha/linux-qualcomm-sm8250 issue 6 and a working OnePlus 8 Pro port) and confirmed in the realme downstream kernel (`drivers/soc/oplus/sensor/oplus_sensor_devinfo.c`, `SMEM_SENSOR = 130`).
- Driver: `drivers/soc/qcom/oplus-sensor-devinfo.c` (kernel fork commit `1136f1896`): trimmed port of the downstream GPL driver (table layout + DT parsing, no procfs/calibration). `CONFIG_QCOM_OPLUS_SENSOR_DEVINFO`. The bootloader does NOT preallocate the item: the driver allocates it (6792 bytes, the 3-sources layout `struct sensor_info`).
- DT: `oplus-sensor` node in `sm8250-realme-bitra.dts`, copied from the stock `kona-mtp.dtsi` (accel icm42607/LSM6DS3C, mag AKM0991X/MMC5603, light+proximity MN78911 on bus 5 irq 129, rear CCT on bus 4).
- Test (image `a-30`, driver as a module): `insmod` after boot, then restart the SLPI and `hexagonrpcd-sdsp` (`rc-service hexagonrpcd-sdsp stop; echo stop/start > remoteproc0/state; rc-service hexagonrpcd-sdsp start`), ~100 s later: `ssccli` returns accelerometer, gyroscope, **proximity (FAR)**, **light (~9 lux indoors)**, **magnetometer (X/Y/Z uT)** and **compass (heading ~289 deg)**; `iio-sensor-proxy` reports accelerometer, ambient light, proximity and compass. Proximity NEAR (covered) and the magnetometer/compass accuracy are not yet verified by hand; the compass needs a mount matrix.
- For boot: the table must exist before the SLPI starts, so the driver is built in (`=y`, the SLPI is a module loaded later); not yet flashed.
- Still open: rear colour/ALS sensor (bus 4), SAR, barometer (not listed in the stock DT for this unit); proximity calibration from the registry (`alsps_platform.prox*`); compass mount matrix; `ACCEL_MOUNT_MATRIX` equivalents for the magnetometer.
- **Mount matrix changed (2026-11-27)**: with the sensor inventory the SLPI applies the stock `sensor-direction = 3` itself (Y and Z change sign, X unchanged), so the old matrix left portrait upside down (landscape fine). New `ACCEL_MOUNT_MATRIX="-1, 0, 0; 0, -1, 0; 0, 0, 1"` (= old x diag(1,-1,-1)); flat screen-up now reads Z +9.7 and `monitor-sensor` reports `face-up`. Owner to confirm portrait.
- **Startup timeline (tools/sensor-timeline.sh, 2026-11-27)**: after the daemon attaches, the first sensor answers at ~109 s and all four at ~118 s (stable across two runs). 0-35 s: the DSP reads the whole registry (~6,000 file opens over FastRPC, 563 entries read repeatedly); 36-105 s: it loads all 91 sensor config JSONs one by one (~0.2 s each) with 4-8 s stalls after kona_qrd_lsm6dsm, kona_qrd_icm4x6xx, kona_sx932x_0, kona_qrd_lsm6dso and kona_qrd_bmi26x_0 (sensors that are probably not on this phone). The daemon is idle (`fastrpc_internal_invoke`) between requests, so the time is spent inside the DSP, not in the daemon. Ideas: serve only the configs this phone needs, check the stalls (probes of absent chips), compare with the Android timeline.
- **Phosh restart ~113 s after boot** is the `bitra-sensors` service (restarts the session once because Phosh only attaches to iio-sensor-proxy at session start and the proxy exits when no sensor exists); it goes away if the sensors are ready earlier or Phosh is made to pick the proxy up later.
- **Pruned configs (2026-11-27): sensors ready ~55 s after the daemon starts instead of ~115 s.** The SSC loads every JSON it is served, so serving only the ones this phone needs removes most of the time (runs measured with `tools/sensor-timeline.sh`, daemon start = 5.4 s): all 91 configs: first sensor 109 s, all four 118 s; 51 configs (no sxr2130_*, no other IMUs/SAR/barometer/heart-rate/hall/wigig/other ALS chips): 62-68 s; 45 configs (also no rear colour sensor, no AKM magnetometer): magnetometer 47 s, accelerometer 52 s, proximity 54 s, light 56 s. The MMC5603 is therefore the fitted magnetometer (AKM not needed), the rear colour sensor (kona_qrd_cct*, tcs3408) is dropped (it never enumerated anyway). What remains: ~27 s registry load (563 entries, needed) and the config phase. Applied on the phone with `tools/sensor-prune-permanent.sh` (dropped files are in `sensors/config-unused/`; restore by moving them back) and in `scripts/build_alpine_rootfs.py` (same list as `tools/sensor-prune.sh`, the reversible bind-mount variant). Readings after pruning: proximity FAR, light 17.8 lux, magnetometer/compass 285 deg, accelerometer Z +9.72.
